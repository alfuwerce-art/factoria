# CubeGame Asset & Animation Factory — спецификация работы и конечной цели
## Как должен функционировать конвейер в зрелом состоянии

**Версия:** 1.0 · 13.11.2026  
**Назначение:** максимально конкретное описание требуемой системы для DeepSeek и будущего M1, не заявка о том, что все её компоненты уже существуют.  
**Связанный документ:** `01_DEEPSEEK_FACTORY_IMPLEMENTATION_TZ.md` — что именно разрешено сейчас подготовить, скачать и протестировать.

---

## 1. Главная итоговая цель

**CubeGame Factory должна стать воспроизводимой локальной системой массового производства оригинальных 3D-ассетов и анимаций для CubeGame.** Её задача — превращать (а) исследовательские модели уже перенесённого Unity-каталога и (б) полностью новые концепты в собственные модели CubeGame с корректной анатомией, модульными деталями, совместимым скелетом, rigging/skinning, выразительными новыми анимациями, оружейными взаимодействиями и готовыми к игровому движку выходами.

**Важнейший критерий зрелости — не число созданных картинок/моделей, а систематическое уменьшение ручных технических исправлений на ОДИН утверждённый игровой ассет при сохранении качества, индивидуальности, воспроизводимости и правовой чистоты.** Производство должно улучшаться после обработки каждой партии: дефект → причина → улучшение общего правила → повторная проверка эталонов → следующая партия.

Цель не требует полной автономии художественного утверждения: художественный контроль, качество движения и оригинальность оцениваются человеком.

## 2. Что считать готовым игровым ассетом

**Не просто 3D-модель**, а связка:

- самостоятельно разработанный финальный mesh, соответствующий художественному языку CubeGame; оригинальные материалы/текстуры и понятные пропорции;
- утверждённая анатомическая категория и указание, **кто это существо**, чем оно отличается визуально и поведенчески;
- модульные части головы/торса/конечностей/аксессуаров с правилами совместимости;
- согласованный `RigArchetype` (или честно зарегистрированный новый) с bind pose, ориентацией, обязательными/необязательными костями;
- корректный skinning/жёсткие attachment-позиции и устойчивые деформации под контрольными позами;
- набор базовых движений, необходимые боевые/действийные анимации, уникальные черты вида;
- крепления оружия, хват двух рук, работа IK и событие контакта/удара;
- технически проверяемый экспорт, данные `EntityRecipe`, игровой prefab (на этапе официальной Unity-интеграции);
- отчёт прохождения тестов, версии всех компонентов, происхождение и лицензии исходных ресурсов.

**Статические ресурсы**, растения, предметы окружения и часть объектов не требуют rig/animation; Factory обязана распознавать этот случай и отправлять их в отдельную ветку производства без искусственных скелетов.

## 3. Два входных пути

### Путь A. Существующий каталог CubeGame — ПРИОРИТЕТНЫЙ

Источник — модели, **уже подготовленные и отображаемые в Unity по контуру M0**, местами декодируемые из локального `.scratch/content`, а не обычные импортированные FBX. Не запускать массовое повторное извлечение Alpha. При необходимости — создать *только техническую рабочую копию* геометрии из текущего Unity/runtime источника. Для юридически самостоятельных финальных ассетов оригинальная Alpha-геометрия используется как исследовательская справка, а не как автоматически разрешённая основа коммерческого меша.

```text
Asset identity из M1-R0 (Alpha name / gameplay role / model mapping)
  → временная редактируемая копия геометрии / документированный reference
  → стиль и новый оригинальный силуэт CubeGame
  → новая модель и модульные body parts
  → ОБЩАЯ ЧАСТЬ C
```

### Путь B. Полностью новый оригинальный вид/модель

```text
Original creative brief (новый вид, среда, повадки, размеры)
  → original concept / reference images
  → 3D creation: Blender procedural / local AI candidate / artist-guided tools
  → clean topology, proportions, modular parts, художественное ревью
  → ОБЩАЯ ЧАСТЬ C
```

Модели, сгенерированные image-to-3D AI, могут иметь слипшиеся конечности, неудачную топологию, материалы и лишнюю геометрию. Это **черновые заготовки**, пока не прошли clean/rig тесты. Различать **3D-to-3D controlled redesign** и **image-to-3D generation**.

## 4. Общая часть C: от готовой геометрии до анимации

```text
C0. Geometry Approved
C1. Anatomy classification + body landmarks
C2. Skeleton contract selection
C3. Skeleton fitting (bones/joints to proportions)
C4. Control rig generation (authoring rig) + export rig definition
C5. Skinning / attachments / modular body bindings
C6. Pose & deformation validation
C7. Base locomotion animation package
C8. Weapon / creature action animation package
C9. Per-identity animation personality layer
C10. Retargeting / IK / grip and action metadata
C11. Export + Unity preview + game runtime tests
C12. Human review + versioned approved asset
```

> **Художественная зависимость [FACT-D17](docs/decisions/FACT-D17-character-visual-first-face-emotions.md):** в будущем сначала создать одну эталонную voxel-модель с выразительным, но пиксельным лицом и раздельными кубическими сегментами конечностей; получить явную визуальную приёмку владельца. Только после неё тестировать эмоции на той же модели, отдельно принимать их качество и затем масштабировать. Не подменять визуальную приёмку техническим PASS и не начинать face-emotion систему во время PREP.

### C0. Geometry Approved

Утверждается **готовая визуально модель**, прежде чем ей подгоняют skeleton. Производство знает требования к будущим движениям заранее (плечи, локти, ширина шага, двуручный хват), но не заставляет художника начать с готовой ригнутой модели.

Выход: чистая геометрия, части тела, preview, список разрешённых деформаций и ограничений.

### C1. Анатомия ≠ identity ≠ интеллект

**Анатомия:** количество ног/рук, крыльев, хвоста, наличие суставов, способ перемещения.  
**Идентичность:** Orc, Elf, Dwarf, Human, Goblin, Wolf, Owl, SandHorror и т.д.  
**Поведение/интеллект:** разумный NPC, примитивный монстр, хищник, пассивное существо.  
**Анимационная личность:** осанка, длина шага, поворот головы, тяжесть движения, приёмы атаки, реакции, уникальные действия.

Ни интеллект, ни название не должны **автоматически** диктовать новый скелет. Например, эльф/орк и человекоподобный монстр могут использовать compatible humanoid skeleton contract, но иметь разные motion/personality profiles. В текущем исследовании M1-R0 — 11 **структурных категорий**, не 11 утверждённых скелетов. Типы `INSECT6`, `ARACHNID8`, `SERPENT` под существующий каталог не подтверждены и нужны лишь при появлении новых соответствующих видов.

**Важно:** результаты M1-R0 ограничены структурой Alpha; пригодность нового единого humanoid rig и перенос анимаций нужно тестировать после редизайна на настоящей геометрии.

### C2. Skeleton Contract

У семейства фиксируются обязательные кости, иерархия, имена, оси, bind/rest pose, размерные диапазоны, sockets, optional bones, экспортный формат. У Human и Orc совместимый контракт, но индивидуально расположенные суставы. Полностью уникальные существа могут получить новый archetype, если прежний несовместим.

**Граничный случай:** «торс + руки без ног» не следует автоматически называть полным humanoid rig без проверки движения и optional bones. Проверить совместимость или назначить другое семейство.

### C3. Fitting Skeleton к готовому mesh

Техническая функция: landmarks (плечо, локоть, кисть, таз, колено, стопа), пропорции → согласованный skeleton → adjusted bone positions. Если AI угадывает положение суставов, оно проходит геометрическую проверку. Не разрешать «каждому автогерою по своему уникальному хаотичному skeleton»: это разрушит библиотеку анимаций.

**Rigify не равен Rig Fitter:** Rigify строит контрольный риг из метарига, но не гарантирует автоматическую классификацию произвольного монстра.

### C4–C5. Rigging и Skinning

На экспорт — стабильный deform skeleton; в Blender — при необходимости отдельный animator control rig. Для rigid voxel segments — жёсткие bone assignments/attachments; для локтей, плеч, таза, гибких мышц — корректно распределённые weights; для аксессуаров, шлемов, доспехов — sockets или специальные правила. Проверить весовые суммы, нулевые группы, залипания деталей, обратные нормали, размеры, оси.

Не рассчитывать на чистый Auto Weights для крупных плеч, доспехов, хвостов, рыб и необычных тел. Коррекции сначала исследуются, затем кодируются как общие семейные правила.

### C6. Pose Validation

Набор диагностических поз: T/A/Rest, подъём рук, двуручный хват, сгибание локтей, шаг, присед, разворот, сильная атака, падение/реакция. Измеримые проблемы: самопересечения, отрыв кисти от оружия, неправильное вращение суставов, растяжение/потеря объёма, clipping, застрявшая экипировка. Если не прошла проверка — `REVIEW_REQUIRED` и категория дефекта.

### C7–C9. Animation Library + индивидуальность

Анимация принадлежит **анатомическому архетипу / оружию / действию / редкому signature**, не каждой отдельной модели. Библиотека новой боёвки создаётся с нуля или с помощью AI черновиков и доработки в Blender/Cascadeur. Alpha анимации изучаем для значения вида, а не используем как конечный стиль боя.

Пример: `Humanoid_Base_Locomotion` и `Humanoid_2HSword` общие Human/Orc/Elf, но Orc получает свою массивную осанку, тяжелые шаги/тайминг, голова и руки — corrections; Elf — другой stride/cadence; Goblin — другую осанку/реакции. Дополнительный clip только когда общего пакета/параметрических вариаций недостаточно для читаемой уникальности.

**Пакет анимации** хранит действие, требования к skeleton/weapon, клип, root motion policy, event markers, timing windows, grip sockets, layers, compatible profiles, version, evidence of validation.

### C10. Retargeting и игровая синхронизация

В Unity в первую очередь Mecanim/Humanoid Avatar + Animation Rigging; для non-humanoids — Generic rig или собственные корректирующие слои по протестированному пути. Retargeting **не** является AI-генерацией новой анимации. Локальный AI не управляет gameplay атакой в реальном времени: gameplay data должна предсказуемо задавать hit timing, startup/active/recovery/cancel windows, а клип правильно синхронизироваться с ними.

### C11–C12. Экспорт, Unity, приёмка

Экспорт в выбранном совместимом формате, контроль осей/единиц, bind/rest pose, анимации, нормалей, материалов, attachments. **Только официально разрешённая стадия Unity integration** создаёт runtime prefab/EntityRecipe и проверяет PlayMode/Player. Даже если модель красиво двигается в Blender, это не доказывает валидность боевой анимации в Unity.

## 5. Исследовательский контур семейств

Существующий M1-R0 — база для будущей переработки. На каждую подтверждённую сущность сохранять:

| Поле | Смысл |
|---|---|
| `alpha_kind / alpha_name` | кем существо является в оригинальной Alpha, с provenance |
| `unity_variant / unity_runtime_ref` | фактическая подготовленная Unity-модель/путь, без выдуманных GUID |
| `anatomy_family` | исследовательская форма тела |
| `identity_family` | визуально-культурное/биологическое семейство |
| `intelligence_behavior_group` | самостоятельный признак, не выбор rig |
| `visual_features` | что делает вид узнаваемым |
| `motion_personality` | предполагаемая осанка, походка, темп, манера боя и signature |
| `rig_archetype_candidate` | гипотеза совместимого скелета, требует теста |
| `source_provenance` | фактическая опора/неизвестное |

Из 156 строк M1-R0 — 130 существ и 26 пассивных объектов; 154 имеют имя из декомпиляции, 2 неизвестны. Важно: `LOCAL_ONLY` описывает локально подготовленные геометрию/клипы, не гарантирует встроенный `.fbx`, корректность Player или разрешение публиковать.

## 6. Масштабирование и автоматическое снижение ручных правок

Для каждого **реального rig/identity семейства**, а не всей мешанины каталога, запускается серия:

```text
Эталон 1 → 2 модели → 5 → 10 → 25 → 50 → контролируемые batch
```

НЕТ текущих требований к проценту успеха, количеству минут, допустимому числу исправлений или условиям перехода. Они **не назначаются** до отдельного решения пользователя.

**Принцип обучения производственного процесса** — не обязательно обучение нейросети. Это цикл инженерной коррекции:

```text
Новая партия
  ↓
Автоматизация + визуальное ревью
  ↓
Отчёт: проблема, стадия, модель, семейство, время исправления
  ↓
Группировка одинаковых проблем
  ↓
Исправление ОБЩЕГО алгоритма/профиля/правила
  ↓
Регрессия на эталоне и уже прошедших моделях
  ↓
Следующая партия с меньшим числом повторных ручных исправлений
```

**Обязательные показатели для сбора (без заданных нормативов):** человеко-минуты на *одну одобренную* модель (включая переделки); доля автоматического первого прохода; среднее число ручных исправлений; частота повторяющихся дефектов; эстетические замечания; rig compatibility; clipping/grip defects; качество новых motion packages; время GPU/CPU и итоговые файлы.

Сохранять manual overrides отдельно от автоматически создаваемых данных; они не должны теряться при перевыпуске. Сравнивать сопоставимые семейства и степень сложности, не смешивать простой rigid creature и custom boss.

## 7. Что именно будет автоматизировано в зрелой Factory

| Действие | Автоматически? | Когда человек обязателен |
|---|---|---|
| Обнаружить/сопоставить source ID | да, при корректном реестре | неоднозначные соответствия |
| Создать рабочую копию | да, после разработки адаптера | если исходник недоступен |
| Предложить новую геометрию | AI / процедурно частично | утверждение оригинального силуэта и деталей |
| Классифицировать знакомое семейство | в основном да | необычная форма/смешанная анатомия |
| Подогнать согласованный skeleton | в основном да при проверенном профиле | плохие landmarks/необычные суставы |
| Назначить rigid/deform skinning | в основном да при проверенном профиле | сложные плечи, таз, массивные доспехи |
| Подключить базовые анимации | да, по контракту | визуальная оценка движения |
| Создать новую signature attack | AI как черновик + DCC refinement | творческая постановка движения и боевой timing |
| Проиграть Unity анимацию | Unity Animator | только настройка/тест |
| Исправить все дефекты без контроля | **нет, не обещать** | утверждение и лечение новых классов ошибок |
| Отчёт, версии, сравнительные метрики | да | продюсер утверждает качество |

## 8. Пример: реальная сущность `OrcMale` из M1-R0

**Исходная identity:** `0x0b OrcMale` из Alpha; **Unity prepared variant:** `d86_kind_0x0b_formula` по опубликованному R0; local-only model assets (проверять фактическое наличие). Не приписывать завершённый rig.

1. Identity Registry предоставляет знания, что это орк, какова морфология и какие отличия от человека допустимы. Это не художественная лицензия на копирование формы.
2. Разрабатывается независимая новая модель Heavy Orc со своим силуэтом, лицом, пропорциями и деталями.
3. Модель разделена на body parts, подготовлены суставы и deform zones.
4. Под неё fitting общего `CG_Humanoid_v1`, при этом размер/длина костей отличаются от Human.
5. Blender создаёт control rig, rigid attachment и deform weights.
6. Проходит локти, плечи, таз, руки и тест двухручного хвата.
7. Подключается оригинальный `Humanoid_Base` и `Humanoid_2HSword`, созданный отдельно на эталонном humanoid.
8. Добавляется Orc motion personality: осанка, сила шага, timing и при необходимости signature attacks. **Не переносить Alpha battle clips как финальный CubeGame combat**.
9. Экспортируются animation-ready model, package mappings, материалы, сведения о происхождении и тесты.
10. После разрешения Unity-интеграции — prefab, gameplay synchronization, player combat test, approval.

Следующая человеческая/эльфийская/гоблинская модель проходит те же контракты без переписывания рига и новой полной библиотеки клипов.

## 9. Пример: совершенно новый паукообразный противник

1. В Creative Brief объявлен оригинальный 8-ногий вид: внешний вид, материалы, размер, PvE роль, анимационные особенности.
2. Создаются оригинальные референсы и 3D геометрия. AI может быть генератором черновика, но финальная форма проверяется.
3. По готовому mesh выбираем `ARACHNID8`. В Alpha-каталоге R0 такой категории **нет**: архетип создаём только на этапе расширения нового контента.
4. Проектируется `CG_Arachnid8_v1` — иерархия восьми ног, тело, head/mandibles при необходимости, ground contacts.
5. Blender fitting/skin weights, затем оригинальные Walk, Turn, Attack, Hit, Death и отличительные движения.
6. Generic-rig подход в Unity, procedural foot placement / IK, боевые events и тесты.
7. После создания эталона другие паукообразные могут пользоваться той же технологией и общим анимационным набором с индивидуальными поправками.

## 11. Архитектура по ответственностям

- **Blender:** editable meshes, bones, deform weights, animation curves, export.
- **Rigify:** управляющие риги для поддерживаемых типов; не магическая AI-система всех существ.
- **Python Blender API:** программный доступ к геометрии, bones, parents, weights, pose tests, export. В PREP не пишем game-specific обработчики.
- **Autorig candidate:** может помогать с joints/skinning; требует проверки лицензии, качества, поддерживаемого skeleton и железа.
- **ComfyUI:** возможный AI-блок геометрии; не replacement for animation runtime/rigging.
- **Cascadeur:** создание и правка анимационных движений, ключевых поз и экспорт.
- **Local motion AI:** черновые skeletal motion, если найдётся совместимая модель; не гарантированный источник финальных ударов.
- **Python runner или n8n:** workflow order, retries, errors, output status; **не** определяет анатомию и не скиндит сам.
- **Unity Mecanim:** воспроизведение и blend/retarget humanoid clips; Generic для иной анатомии.
- **Unity Animation Rigging:** IK corrections, grips, look-at/secondary constraints.
- **CubeGame data/validators (будущее):** anatomy/identity matching, rig fitting profiles, animation package lookup, gameplay hooks, review and regressions.
- **DeepSeek:** настройка инструментов и подготовка исследования; впоследствии анализ отчётов, автоматизационные скрипты по отдельному этапу.

## 12. Как выглядит наблюдаемый workflow зрелой системы

**Предполагаемый UI, не реализовано:**

- `Asset ID`, вид/семейство, verified source, выбранный режим обработки;
- миниатюра текущей геометрии и видимые промежуточные версии `Source → Redesigned → Rigged → Animated → Unity Preview`;
- выбор rig contract и профиля модулей;
- индикатор выполнения, журнал ошибок и статусы `NOT_STARTED`, `IN_PROGRESS`, `REVIEW_REQUIRED`, `FAILED`, `PASS`;
- пауза на художественное утверждение геометрии и новой уникальной анимации;
- кнопки `Review`, `Retry Stage`, `Export Approved`, `Compare Batch`;
- список применённых автоматических правил и сохранённых ручных исправлений;
- отчёт времени/ошибок на каждый этап.

**НЕ нужно** сразу создавать сложный UI. Приоритет — доказанный воспроизводимый CLI/скриптовый конвейер. Готовую нодовую систему подключить, только если ускорит результат.

## 13. Что не должно произойти

1. Перенос Alpha в Unity не должен остановиться из-за исследовательской Factory.
2. Нельзя публиковать защищённые файлы Alpha или выдавать их механический ремеш за оригинальный ассет.
3. Не считать 156 видов=156 rig contracts либо 106 семейств Alpha-motion=106 новых animation libraries.
4. Не генерировать анимации по отдельности каждому орку, если есть общий совместимый clip + personality corrections.
5. Не использовать один humanoid skeleton на рыб, птиц, пауков и бесполых floating существ без анатомической проверки.
6. Не требовать отдельной AI-модели для задач, которые уже надёжно делает Blender/Unity.
7. Не утверждать автоматически GPU-совместимость 3D/AI motion моделей с 8GB VRAM.
8. Не стирать ручные корректировки при повторном запуске.
9. Не задавать сейчас числовые условия расширения партии.
10. Не обещать, что всё полностью локально/бесплатно/однокнопочно до реальных тестов и проверки лицензий.

## 14. Итоговые цели по стадиям (без формальных порогов)

**Во время M0 — Factory PREP:** все основные программы и версии обследованы, разрешённые инструменты установлены и прошли тесты на независимых ассетах; обнаружены ограничения, документированы будущие интеграционные интерфейсы. Игровой CubeGame не изменён.

**После открытия M1 — Prototype Factory:** на оригинальном Human Standard отработана вся цепочка; на Orc Heavy доказано переиспользование humanoid skeleton/locomotion/combat; качество проверено в Unity; затем аналогичные эталоны по доступным семействам.

**При масштабировании M1 — Production Factory:** каждое семейство получает утверждённые профиль анатомии, rig, правила skinning и библиотеку анимации; партии `1→2→5→10→25→50→batch` используются для накопления общих исправлений. Ручных технических действий на одну одобренную модель становится меньше, уникальность видов не теряется.

**После переработки существующего каталога — New Content Factory:** оригинальный новый вид с нуля проходит тот же геометрический → риг → анимационный → Unity маршрут; новый skeleton добавляется только при реальной необходимости. Система обеспечивает долгосрочное массовое создание существ, NPC и моделей без новой отдельной производственной технологии на каждый вид.

**Окончательное определение успеха:** достаточно дать Factory описание существа, подтверждённую исходную модель или оригинальный concept, выбрать режим и family profile, после чего система **самостоятельно выполняет все уже изученные повторяемые технические операции**, останавливается в точках художественной приёмки и выпускает качественный игровой ассет с правильными скелетом, движениями, индивидуальностью, оружейными взаимодействиями и отчётом. После каждой партии повторяющиеся ошибки устраняются на уровне Factory, а не ручной правкой каждой следующей модели.
